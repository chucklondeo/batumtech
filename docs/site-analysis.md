> 文档状态：初步分析（基于当前工作区扫描结果与项目背景）

## 1. 执行摘要

Batumtech.com 计划从旧有 PHP CMS + MySQL 升级为 Next.js 15 + TypeScript + Payload CMS。迁移的首要原则不是简单重建页面，而是保持现有业务资产的连续性：历史 URL、百度收录与排名信号、产品及内容数据、图片资源，以及未来香港、新加坡站点的扩展能力。

当前工作区扫描显示：目录中仅存在一个尚无提交记录的 `.git` 目录；未配置 Git remote，也没有检出的 PHP 源码、数据库导出、Web 服务器配置、URL 清单或 `uploadfile/upfiles` 图片目录。因此，本报告可确定目标架构与迁移方法，但无法在本阶段给出真实记录数、字段映射、现存 URL 规则、重复/缺失图片数量等实测结果。上述内容必须在取得生产代码及只读数据快照后补充验证。

推荐采用“盘点与冻结 → 迁移演练 → URL 对照验证 → 预发布抓取验收 → 受控切换 → 持续监控”的迁移路径。上线前必须形成逐条 URL 映射表，旧 URL 优先保持不变；确需变化时实施单跳、永久 301，并长期保留。

## 3. 技术架构分析

### 3.1 旧架构初判

依据背景，旧站属于典型 PHP CMS 单体架构：PHP 同时负责内容管理、模板渲染和访问路由，MySQL 保存结构化内容，图片以本地文件形式保存在 `uploadfile/upfiles`。这种模式的迁移风险主要集中在隐式 URL 规则、数据库字段语义与文件路径之间的耦合。

在未取得源码前，不应假定任何表字段、主键关系或路由格式。尤其需要核实：分类是否使用邻接表/路径字段、内容是否存在软删除和发布状态、富文本是否嵌入相对图片路径、URL 是否由数字 ID/拼音/slug 生成，以及旧系统是否存在多套重复入口。

### 3.2 目标架构建议

建议采用一个可支持多站点的单体仓库，并把“站点”作为一等内容维度：

- **前端与服务端渲染**：Next.js 15 App Router + TypeScript；内容页采用 SSR、ISR 或静态生成的组合，确保搜索引擎可直接获得完整 HTML。
- **内容平台**：Payload CMS，统一管理产品、新闻、案例、分类、媒体、站点配置、SEO 字段和重定向规则。
- **数据库**：建议使用 Payload 官方支持且团队可稳定运维的数据库适配器。是否继续使用 MySQL 必须以目标 Payload 版本的官方兼容性验证为准；如选 PostgreSQL，应把旧 MySQL 仅作为迁移源，不进行双向同步。
- **媒体存储**：生产环境优先使用 S3 兼容对象存储/CDN；保留原相对路径或建立不可变的旧路径映射，避免图片 URL 大规模变化。
- **缓存与发布**：按内容变更触发精确 revalidation；页面缓存、CDN 缓存和媒体缓存分别管理。
- **搜索与观测**：建立结构化日志、404/5xx、重定向命中、Core Web Vitals、抓取状态和 sitemap 提交监控。

### 3.3 建议的 Payload 内容模型

| Collection / Global | 用途 | 关键字段建议 |
|---|---|---|
| `sites` | 多站点主体 | code、域名、地区、默认语言、时区、品牌配置、启用状态 |
| `products` | 产品 | legacyId、site、title、slug、category、summary、content、media、SEO、publishedAt、status |
| `news` | 新闻 | legacyId、site、title、slug、category、excerpt、content、cover、SEO、publishedAt、status |
| `cases` | 案例 | legacyId、site、title、slug、category、content、gallery、SEO、publishedAt、status |
| `categories` | 分类树 | legacyId、site、type、parent、name、slug、sort、SEO |
| `media` | 图片与附件 | legacyPath、file、alt、width、height、hash、mimeType、siteScope |
| `redirects` | 迁移规则 | source、destination、statusCode、site、reason、verifiedAt |
| `site-settings` | 站点配置 | site、公司资料、导航、页脚、默认 SEO、统计配置 |

所有迁移集合均应保留 `legacyId` 和必要的 `legacyPath`，且设置唯一索引（通常为 `site + legacyId`、`site + slug`）。这会使迁移脚本可重复执行、可审计、可回滚，而不是一次性不可追踪的导入。

### 3.4 香港、新加坡多站点设计

建议采用“共享平台、站点隔离、内容可选择复用”的模型，而不是未来复制多套代码与数据库：

- 域名到 `site` 的解析放在统一站点注册表中，不在业务代码里散落判断。
- 产品可设计为全局主数据加站点本地化覆盖；新闻和案例默认归属单一站点，也可显式共享。
- 每个站点独立配置导航、联系方式、法律声明、默认 SEO、sitemap 和 robots 策略。
- URL 的域名方案需业务确认：地区独立域名通常比路径式结构更符合独立品牌/运营需求；无论采用何种方案，都避免用 IP 自动跳转搜索引擎。
- 语言与地区不是同一概念。为未来预留 locale，但不要把香港/新加坡直接等同于繁体中文/英文。
- 若存在同语言近似页面，使用正确的 canonical 与 `hreflang`（例如 `zh-CN`、`zh-HK`、`en-SG`，以及适用时的 `x-default`）。

## 4. 数据库分析

### 4.1 已知表的预期职责与核查重点

以下仅为基于表名的工作假设，必须由真实 DDL 和数据样本确认：

| 旧表 | 预期内容 | 重点核查 |
|---|---|---|
| `web_product` | 产品内容 | ID、分类键、标题、slug/文件名、正文、参数、主图/图集、排序、状态、发布时间 |
| `web_news` | 新闻内容 | ID、分类键、标题、摘要、正文、来源、作者、封面、发布时间、状态 |
| `web_case` | 客户案例 | ID、分类键、标题、正文、行业/产品关系、图片、发布时间 |
| `web_category` | 分类体系 | 内容类型、父级关系、路径/层级、slug、模板、排序、状态 |
| `web_config` | 全站配置 | key/value 类型、序列化格式、公司资料、SEO 默认值、路径与功能开关 |

### 4.2 必做的数据剖析

迁移前应在只读副本执行并归档：

- 每张表的 DDL、行数、主键、索引、外键（包括应用层隐式外键）。
- 数据库、表和列字符集/排序规则，重点排查 GBK、GB2312、UTF-8 混用及乱码二次编码。
- NULL、空字符串、`0`、默认日期等历史占位值的真实语义。
- 重复标题、重复 slug、重复 URL、孤立分类、循环分类和无效父节点。
- 发布/草稿/删除状态及时间字段的时区。
- 正文中的 HTML、内联样式、短代码、绝对/相对链接和图片路径。
- 数据库图片引用与磁盘文件的双向差集：有引用无文件、有文件无引用。
- `web_config` 中 PHP serialize、JSON 或自定义分隔格式，禁止未经验证直接解析。

### 4.3 字段映射原则

先建立版本化的数据字典和字段映射表，再开发迁移程序。映射表至少记录：源表/字段、目标集合/字段、转换规则、默认值、空值策略、校验规则、失败处置及样例。

原始主键不得丢失；迁移后每条记录应能从 `legacyId` 追溯至源记录。分类关系应先迁移并形成旧 ID 到新 ID 的确定映射，再迁移产品、新闻和案例。SEO 字段、发布时间、排序和发布状态属于业务数据，不能只迁移标题与正文。

## 5. 数据迁移计划

### 阶段 A：源数据冻结与基线

1. 在不影响生产的前提下取得 MySQL 一致性快照和图片目录快照。
2. 生成数据库表行数、关键字段非空率、重复率和关联完整性报告。
3. 对图片生成 manifest：原始相对路径、字节数、MIME、宽高、mtime、SHA-256。
4. 抓取旧站全部可访问 URL，并合并 sitemap、日志、百度导出、数据库推导 URL，形成基线 URL 库。

### 阶段 B：转换与清洗

迁移顺序建议为：`sites` → `categories` → `media` → `products/news/cases` → `site-settings` → `redirects`。

- 迁移程序必须幂等；重复运行更新同一目标记录而不生成副本。
- 原始导出保持只读，所有清洗通过转换层完成并产生日志。
- 富文本中的站内链接和图片引用使用解析器处理，不做盲目的全局字符串替换。
- 文件以哈希去重，但对外仍保留旧路径别名；不要因去重改变公开 URL。
- 对不支持或损坏的图片单独隔离并输出人工处置清单。
- 图片 `alt` 优先继承原数据；缺失项列入内容补全清单，不用文件名机械填充。

### 阶段 C：验证与对账

每次演练至少输出以下对账指标：

- 各内容类型源记录数、成功数、跳过数、失败数及差异原因。
- 分类关联成功率、孤立记录数。
- 媒体引用总数、成功解析数、缺失文件数、重复文件数、哈希不一致数。
- 标题、正文、发布时间、发布状态、SEO 字段的抽样及自动校验结果。
- 所有目标公开 URL 的 HTTP 状态、canonical、标题、H1、图片响应和内链有效性。

数据库行数相同不是充分验收条件；需要对关键字段做规范化哈希或逐字段对账。任何失败必须可定位到旧表、旧 ID 和旧路径。

### 阶段 D：正式切换

1. 在预发布环境完成至少一次全量演练并固化迁移版本。
2. 上线窗口前做最终备份和短时内容冻结，记录明确的数据截止时间。
3. 执行全量或“已验证全量 + 最终增量”迁移。
4. 自动跑 URL、内容、媒体、SEO 与性能冒烟测试。
5. 切换流量后保留旧系统只读备份，不再公开提供可被索引的副本。

### 回滚原则

- DNS/CDN/反向代理切换需可快速回指旧站。
- 新数据库和对象存储使用独立命名空间，不覆盖唯一的旧数据副本。
- 回滚后禁止在新旧 CMS 同时编辑，以免形成不可合并的数据分叉。
- 回滚触发条件应在上线前量化，例如关键页面 5xx、核心 URL 大面积异常、媒体缺失或数据对账失败。

## 6. URL 迁移计划

### 6.1 URL 清单与分级

最终 URL inventory 应合并五类来源：数据库推导、站内全量抓取、XML sitemap、服务器日志、百度搜索资源平台/外链数据。每个旧 URL 保存以下信息：

- 原 URL、规范化 URL、HTTP 状态和最终落点。
- 页面类型、旧记录 ID、新记录 ID、新 URL。
- 是否被收录、搜索点击/展现、访问量、外链、业务优先级。
- 迁移动作：保持、301、410、修复或人工确认。

优先级建议：有自然搜索流量/外链的页面 > 已收录内容页 > 站内可达页 > 无价值参数与重复页。

### 6.2 映射策略

1. **能够保持的 URL 原样保持**：路径、大小写、扩展名和尾斜杠均视为 URL 契约的一部分。
2. **有等价新页面的旧 URL**：一对一 301 至语义最接近的新 URL。
3. **多个重复旧 URL**：分别单跳 301 至唯一 canonical 页面。
4. **无等价内容但有价值的页面**：优先补建内容；不能补建时跳到真正相关的上级分类，而非统一跳首页。
5. **永久删除且无替代价值的页面**：返回 410（或稳定 404），不要伪装成 200。
6. **查询参数**：只移除已确认无语义的追踪参数；筛选、分页或内容参数需逐类评估。

### 6.3 301 实施要求

- 重定向规则以版本化 CSV/数据库表作为单一事实来源，建议字段：`source_path`、`source_query_policy`、`destination_url`、`status_code`、`content_type`、`legacy_id`、`reason`、`verified`。
- 在 CDN/反向代理层优先处理大规模静态映射，应用层处理内容驱动规则；避免每次请求全表扫描。
- 只允许单跳：旧 URL → 最终 200 URL；不得出现 301 链、循环、协议链或跨域往返。
- 保留原 query string 与否需要按规则显式定义。
- 301 应长期保留，不应在搜索引擎刚完成迁移后删除。
- 上线前对完整映射集自动测试状态码、Location、最终状态、canonical 和循环。

### 6.4 待确认的旧 URL 规则

因缺少代码与线上抓取数据，目前不能安全拟定具体 rewrite 规则。后续至少要识别：产品/新闻/案例详情、分类页、分页页、搜索页、标签页、附件页、旧 `.php` 入口、数字 ID 参数、伪静态后缀、移动端路径和历史域名变体。

## 7. SEO 保护计划

### 7.1 上线前基线

- 导出现有关键词、点击、展现、平均排名、索引量、抓取异常和外链。
- 保存核心页面 HTML/截图及 title、meta description、H1、canonical、robots、结构化数据、正文长度和内链。
- 对高价值 URL 设置逐页验收，不仅抽样。
- 抓取旧站 HTTP 状态与响应头，记录 www、HTTPS、尾斜杠和大小写规范。

### 7.2 页面级信号继承

- 尽量保留原 URL、title、H1、核心正文、发布时间、图片和站内锚文本。
- 每个可索引页面使用自引用 canonical；canonical 必须指向最终 200 页面，不能与 301/robots/noindex 冲突。
- 服务器返回完整可索引 HTML；核心内容、链接和元数据不依赖客户端 JavaScript 执行后才出现。
- 保留并校正面包屑、相关推荐、分类导航等历史内链结构。
- 输出与页面类型匹配的 JSON-LD，并以真实可见内容为依据。
- 为图片保留稳定 URL、alt、尺寸和可访问性，避免 robots 或鉴权阻断百度图片抓取。

### 7.3 技术 SEO

- 生成按站点拆分的 XML sitemap，只包含 canonical、200、允许索引的 URL；大型站点使用 sitemap index。
- `robots.txt` 按站点生成，并引用对应 sitemap。预发布环境必须禁止索引，正式上线时自动验证已解除阻断。
- 统一 HTTPS、主机名、大小写、尾斜杠和默认首页策略。
- 404 页面返回真实 404；不要产生 soft 404。
- 分页、筛选、站内搜索和参数组合需防止无限抓取空间。
- 控制页面性能与稳定性，重点验证 LCP、INP、CLS、TTFB、图片优化及移动端体验。

### 7.4 百度专项保护

- 保持百度搜索资源平台站点验证方式在切换后仍有效。
- 提交新 sitemap，并使用平台可用的普通收录/快速收录能力；具体接口和配额应在实施时以当时官方规则为准。
- 不依赖 JavaScript 重定向或 meta refresh；使用服务端 301。
- 检查百度蜘蛛是否被 CDN/WAF、地区策略、频率限制或 User-Agent 规则误拦截。
- 若主域名不变，不使用“网站改版”工具替代逐 URL 的正确 301；若域名或路径体系显著变化，再根据届时百度平台能力提交改版规则。
- 切换后持续跟踪抓取频次、索引量、品牌词和核心非品牌词，不以短期首页可访问作为迁移成功标准。

### 7.5 上线后监控节奏

- **首 72 小时**：高频检查 5xx、404、重定向、robots、sitemap、核心页面渲染和媒体缺失。
- **前 4 周**：每日/每周比较索引、点击、展现、排名、爬虫访问和新旧 URL 命中。
- **1–3 个月**：按页面类型和目录评估恢复趋势，修复重定向覆盖缺口和内容质量问题。
- 保留迁移前基线和每次规则变更记录，以便区分迁移影响、算法波动与季节变化。

## 8. 关键风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 当前缺少真实源码与数据 | 分析无法落到字段和 URL 级别 | 获取只读快照后补做实证盘点，不依据表名直接开发 |
| URL 规则遗漏 | 百度排名、外链价值与流量损失 | 多来源合并 URL inventory，逐条映射与自动验收 |
| 字符集/富文本转换错误 | 中文乱码、正文或链接损坏 | 原始字节级备份，显式转码，DOM 解析与抽样校验 |
| 图片路径改变或丢失 | 页面破图、图片搜索价值下降 | 文件 manifest、哈希校验、旧路径兼容和 CDN 验证 |
| 分类关系不完整 | 内容孤立、内链变化 | 先迁分类、关系对账、孤儿清单与人工处置 |
| 多站点模型后补 | 后续复制系统、内容混乱 | 首版即引入 `sites` 维度与域名/locale 配置 |
| 301 链或泛化跳首页 | 信号衰减、soft 404 | 一对一单跳映射，最终目标必须 200 且语义相关 |
| 预发布或新站误设 noindex | 全站无法收录 | 发布门禁自动检测 robots、meta robots、响应头 |
| 同时改 URL、内容和视觉 | 难以定位 SEO 波动原因 | 核心页面优先保持 URL 与主题，分阶段优化内容 |

## 9. 验收门槛建议

正式切换前建议至少满足：

- 已知高价值旧 URL 100% 有明确处置，且所有 301 均为单跳。
- 所有计划收录的新 URL 返回 200，canonical、robots 和 sitemap 一致。
- 产品、新闻、案例、分类的数据对账无未解释差异。
- 数据库所引用的生产媒体 100% 可访问；任何缺失均有批准的处置记录。
- 核心页面内容、title、H1、发布时间和结构化数据通过自动与人工检查。
- 不存在全站级 noindex、robots 阻断或 WAF 误拦主要搜索引擎蜘蛛。
- 已完成备份、恢复演练、切换手册、回滚手册和负责人确认。
